# Validation (`validation.py`, `/validate`)

`/validate` scores how well the loaded model picks and calls tools, to guide fine-tuning ([FINE-TUNING.md](../FINE-TUNING.md)). Run it once per model and compare the Full scores. Treat a gap under about 5 points as no real difference, since each model gets one pass. `Chat.command_validate` opens `ValidationScreen` (categories, all ticked), `Chat.run_validation` drives a `validation.Run`, and the report goes in the chat without entering the conversation. `ctrl+c` stops the run and saves what finished. Settings can't be opened during a run.

**A run.** Each case is a fresh `Conversation` with its `tool_runner` and `tool_selector` replaced, so the real turn loop and router run. Tools are fake: the runner is the real `tools.run_tool` with `results` set, so an unknown tool or wrong arguments get the same text as in use, and a valid call returns the case's `results` or the file's `default_results` without reaching a backend. `Run` sets the `Assistant` preset, turns routing on, and freezes the clock (`clock.frozen_at`) to the file's `now` and `timezone`, restoring them afterwards. The router chooses first and its choice is recorded. The case's expected groups, or its `tempt` groups on a `no-tool` case, are then added, so every case tests the model.

**Cases (`validation_cases.json`).** These are a held-out test set: never train on them word for word. `parse_suite` rejects a bad file before a run. An entry in `expect` is a required step, and a list inside it gives acceptable alternatives (the first is the tool the step counts for). Other fields: `ordered`, `forbid`, `arguments` (tool → parameter → text the value must contain, ignoring case, or a list of acceptable texts), `carry` (same shape, the value must be in an earlier step's result), `results`, `history` (scripted `{question, reply}` turns), `tempt`, `claim_patterns`. Dates are written against `now`. Categories: `explicit`, `paraphrased`, `obfuscated` (one each per tool), `follow-up`, `no-tool`, `chained` (always ordered), `after-result`.

**Scoring (`validation.score`).** Tool pass: the right tools ran, in order when required. Full pass: also the argument checks, carried values and no false claim. Tool score and Full score are the mean of the category pass rates, so a small category counts as much as a large one. Speed, tokens and router misses never count. A server error makes the case `error`, leaves it out, and marks the run `not comparable`. A failure gets the first label that fits: `false_claim`, `asked_for_value`, `missed_call`, `over_call`, `wrong_tool` (or `broken_chain` once a chain has started), `bad_arguments`, `broken_chain`, `looped`. `false_claim` and `asked_for_value` go by wording, so check the saved replies before trusting those counts. Text before a tool call is reported as a narration rate and doesn't fail a case.

**Files (`validation_results/`, gitignored).** `<timestamp>-<model>.json` has the scores, settings, and each case's calls, reply and label. `<timestamp>-router.json` has one record per case for tuning the router: question, previous question, expected and chosen groups, similarity scores and `missed`, `extra` or `correct` (`error` if it couldn't run). A stopped or filtered run is `partial`.

**Tests.** `tests/test_validation.py` fakes only the model and embeddings, and `CaseFileTest` checks the real case file, including that a perfect model passes every case. `tests/test_validation_ui.py` drives `/validate` with the pilot.
