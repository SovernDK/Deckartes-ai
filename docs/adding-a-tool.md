# Adding or changing a tool

## Adding a tool

Write an async function in `tools.py` with type hints and a Google-style docstring (`Args:` section), decorated with `@tool("<group>")`. Its body is one call to the backend, whose public function takes the tool's arguments and returns the tool text; fetching, normalising and wording stay private to the backend. The decorator adds it to `TOOLS`, `TOOLS_BY_NAME` and its group in `tool_groups.GROUPS` (`tool_groups.py`, with the routing examples), and rejects a group that doesn't exist. `TOOLS` keeps definition order, which is the order the model sees the tools in. `tool_schema.py` generates the schema the model sees from the name, signature and docstring, and marks every parameter as required, even with a default, unless its type allows `None`, so keep parameters few. Make a value the model often lacks optional (`add_calendar_event`'s end), because LFM3 asks the user for required values rather than working them out. Backends run blocking work with `asyncio.to_thread` themselves, and cap the size of returned text (see `web_search.MAX_PAGE_CHARS`) so results fit the context window. Docstrings say "home server (thinkpad)" vs "this computer" so the model can tell the Glances tools and the disk tools apart. Give each common question its own tool that answers it directly (e.g. `get_next_episode(name)`, not "check `get_anime_airing_on` day by day"). When a small model can't find the answer in a tool result, it makes one up, e.g. taking another row's time. For the same reason, return an explicit note when nothing is found rather than an empty list. Prefer returning short plain text with readable units (GB, %, °C) over raw API JSON, and include the reference values a model would otherwise guess, like limits and totals. `run_tool` passes `str` results through as-is and JSON-encodes anything else. Pick a fitting group or add a new one with its own example questions; `@tool(None)` puts a tool in no group, so it's sent with every question. A new tool also needs a default result and explicit, paraphrased and obfuscated cases in `validation_cases.json` (`tests/test_validation.py` fails without them, see [validation.md](validation.md)).

## Tool tests (`tests/test_*_tools.py`)

The wording and order of tool text are load-bearing, so these tests call the tools themselves with fake backend data and assert the exact text, and a wording change fails a test on purpose. Use `HttpTest.serve` (`tests/http_fake.py`) for HTTP responses and `freeze` (`tests/frozen_clock.py`) for the time and time zone. For calendar tests see `docs/calendar-tests.md`. `tests/test_disk_tools.py` uses a real temporary folder.

## Confirmation (`confirm`)

A tool that changes something outside the app declares a keyword-only `confirm: Confirm` parameter and passes it to its backend, which awaits `confirm(question)`. The model never sees it: `tool_schema.model_signature` leaves it out of the definition and of the argument check. The front end running the turn passes its own `confirm` to `Conversation.stream_reply`, which hands it to `tools.run_tool`. `Chat.confirm` pushes a `ConfirmScreen` (y / n / escape) and awaits a future its dismiss callback resolves; interrupting while asking closes the popup. The Telegram bot asks with Yes and No buttons (`docs/telegram.md`). A turn without one (`/validate`, tests, a new front end that doesn't pass it) gets such tools refused by `run_tool` before the backend runs, with tool text saying confirmation can't be asked for here.

## Running a call (`tools.run_tool`)

`run_tool(name, arguments, confirm=None, *, results=None)` is the one place a model's call becomes tool text: arguments that weren't valid JSON (`None`), an unknown name, arguments that don't fit the signature, the missing confirmation, and `Tool X failed: <error>` for a raised exception. Non-text results are JSON-encoded. `/validate` passes `results`, which gives the result once the call has passed those checks, so the model sees the same failure text in validation as in use.
