# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

Deckartes is a terminal chat UI (Textual) for local Ollama models, with tool calling: the model can query a home server's Glances API, scan the local disk, search the web through Ollama's web API, look up anime seasons, timetables and ratings on AnimeSchedule.net, get Counter-Strike esports teams, players and matches from PandaScore plus Valve's ranking, and read and add events in Apple Calendar.

## Commands

There is no build step, test suite, linter or requirements file. Dependencies live in `venv/` (textual 8.2.8, textual-dev, ollama 0.6.3, httpx, pyobjc-framework-EventKit 12.2.2, pypdf 6.20.1, cryptography 50.0.2 for AES-encrypted PDFs).

```bash
venv/bin/python main.py                 # run the app
venv/bin/textual run --dev main.py      # run with devtools; pair with `venv/bin/textual console` in another terminal to see logs/print output
```

Runtime requirements: Ollama on `localhost:11434` with the embedding model `config.embed_model` (`all-minilm:33m`) pulled for tool routing (without it every allowed tool is sent) and `config.rag_embed_model` (`embeddinggemma-2:570m`) for long loaded files, Glances on `http://thinkpad:61208` (only for the server tools), `OLLAMA_API_KEY` (web tools) `ANIMESCHEDULE_TOKEN` (anime tools) and `PANDA_SCORE_API_TOKEN` (CS tools) in the environment or `.env`, and macOS calendar access for the terminal app (calendar tools).

Verify UI changes headlessly with Textual's pilot instead of launching the app:

```python
app = DecartesApp()
async with app.run_test(size=(100, 30)) as pilot:
    app.query_one(Input).focus(); app.query_one(Input).value = "hi"
    await pilot.press("enter"); await app.workers.wait_for_complete(); await pilot.pause()
    app.save_screenshot("shot.svg")
```

`Input` has to be focused before `pilot.press("enter")` or nothing is submitted. Patch `conversation.stream_response` (the name imported into `conversation`, not `ollama_api.stream_response`) to fake model output. History is `app.query_one(Chat).conversation.history`.

## Architecture

Flat modules, no package. `main.py` → `app.py` (`DecartesApp`: bindings, model-picker, help and file-explorer screens) → `chat.py` (widgets: bubbles, spinner, busy state, interrupt) → `conversation.py` (`Conversation`: history, turns and the loaded file, no UI; `rag.py` reads and searches the file) → `ollama_api.py` (model calls) → `tool_router.py` (picks tool groups per question) → `tools.py` (tool registry) → `glances_api.py` / `disk_scan.py` / `web_search.py` / `animeschedule_api.py` / `cs_api.py` / `calendar_api.py` (tool backends).

**Shared config.** `config.py` exposes a single mutable `config` instance (host, model, context_length, temperature, system_prompt, plus tool settings and keys). Modules read it at call time rather than taking parameters; widgets change settings by assigning to it (e.g. the model picker sets `config.model`). Ollama clients are cached per `config.host` in `ollama_api`, so changing the host takes effect on the next call. `ollama_api.model_options()` sends `context_length` as `num_ctx` on every chat call (Ollama's 4096 default is too small for tool results), and `temperature` unless it's `None` (the model's default). The config popup (`config_screen.py`, key `c`) edits `system_prompt`, `temperature` and `context_length`; it checks every field before applying any. `context_length` is picked from `config.CONTEXT_LENGTHS` (2K-32K; add values there), and a value set to something else in `config.py` is kept as an extra option. Options under `RECOMMENDED_MIN_CONTEXT` are labelled "little room with tools". The context also decides whether a loaded file is sent whole (`rag.WHOLE_FILE_SHARE`), but only when the file is loaded.

**Prompt presets.** `prompts.json` holds presets (name, description, `prompt`, `tools`: `"all"`, a list of tool names, or `[]`), selected by `config.system_prompt`. `prompts.py` re-reads the file on every use, so edits apply without a restart. `system_message()` always starts with the current local date and time, even when no preset matches, since models don't know it otherwise. Presets shouldn't repeat it. `Conversation.messages_for` puts the system message first on every turn (it isn't stored in the history), and `ollama_api.active_tools()` sends only the tools the preset allows. A new tool must also be added to the relevant presets, unless they use `"all"`.

**Error contract.** `ollama_api` never raises to the UI: `stream_response` yields, and `fetch_response` returns, a string starting with `**Error:**` (`error_message` / `is_error`). `Conversation` relies on this to show errors in the reply and keep failed exchanges out of history. Tool failures are different: `tools.run_tool` turns exceptions into a text result that goes back to the model, not the user.

**Tool loop.** `stream_response(messages, on_tool)` / `fetch_response(...)` send `tools=TOOLS` (only if the model's Ollama capabilities include `tools`; checked once per host+model), run any tool calls, append assistant + `role: tool` messages to a local copy of `messages`, and repeat up to `MAX_TOOL_ROUNDS`. `on_tool(name)` / `on_tool(None)` drive the spinner label. `fetch_response` is the blocking variant; it calls `on_tool` from its worker thread (`Conversation.reply` handles that).

**Adding a tool.** Write an async function in `tools.py` with type hints and a Google-style docstring (`Args:` section), and add it to `TOOLS`. Ollama generates the schema the model sees from the name, signature and docstring, and marks every parameter as required even with defaults, so keep parameters few. Run blocking work with `asyncio.to_thread`, and cap the size of returned text (see `MAX_PAGE_CHARS`) so results fit the context window. Docstrings say "home server (thinkpad)" vs "this computer" so the model can tell the Glances tools and the disk tools apart. Give each common question its own tool that answers it directly (e.g. `get_next_episode(name)`, not "check `get_anime_airing_on` day by day"). When a small model can't find the answer in a tool result, it makes one up, e.g. taking another row's time. For the same reason, return an explicit note when nothing is found rather than an empty list. Prefer returning short plain text with readable units (GB, %, °C) over raw API JSON, and include the reference values a model would otherwise guess, like limits and totals. `run_tool` passes `str` results through as-is and JSON-encodes anything else. Put the tool in a `TOOL_GROUPS` group (or a new group with its own example questions), otherwise it's sent with every question.

**Tool routing (`tool_router.py`).** Tool definitions are most of the prompt (~2,700 tokens for all tools, against 90 for "hi" without them). So `active_tools(messages, usage)` narrows the preset's tools to the groups `route()` picks. It embeds the question with `config.embed_model` and compares it with each group's `examples` and with `NO_TOOL_EXAMPLES`. Groups at or above `CONFIDENT` and within `MARGIN` of the best are sent. Otherwise small talk gets no tools, a vague follow-up borrows the previous question's scores (`PREVIOUS_WEIGHT`), and an unsure question gets the top `UNSURE_GROUPS` groups, because unknown names (a player, a show) score low. Thresholds were tuned on a 30-question test set plus follow-ups. Re-tune them if you change the embedding model or the examples, and add examples rather than lowering thresholds. Routing is skipped when the preset's tools sit in a single group, and any router error falls back to every allowed tool. Embeddings use the sync client in `asyncio.to_thread`, because `fetch_response` calls `asyncio.run` per turn and the cached async client is bound to the first loop. Example embeddings are computed once per host+model. The chosen groups land in `Usage.tool_groups` and show on the usage line ("tools: cs").

**Server tools (`glances_api.py`).** Each function returns a few lines of text, because raw Glances JSON is mostly counters and byte values (the containers endpoint alone is ~8,000 tokens). The `_format_*` helpers take an endpoint's JSON, so `overview()` reuses them with one `asyncio.gather` over every endpoint. `get_server_overview` answers "how is the server?" in one call instead of a chain of tool rounds. Glances runs in a container on the server, so file systems are de-duplicated by device: its mount points are bind mounts like `/etc/hosts`. Container lines leave out the uptime most of them share (it's given in the summary line). Temperatures include the sensors' warning level so the model doesn't invent one.

**Anime tools (`animeschedule_api.py`).** Results are slimmed to name/rating/episodes/date and rated shows at or below `config.anime_min_rating` (0–10 scale, converted from the API's 1–100) are dropped. Unrated shows (`ratingCount` 0) stay, with `rating: None`, and sort last. They also sort last on the API side, so every page of a list is fetched. Timetables have no ratings, so they're matched by `route` against all `ongoing` anime, because season lists only contain premieres from that season. Timetable `week` is the ISO week, and `subPremier` is `0001-01-01` when unset. `top_season_anime` takes relative seasons ("next", "previous") so the model doesn't do season arithmetic. Upcoming seasons have few ratings, so it fills the top N with unrated shows by `trackedCount` and says so in a `note`. `continues_next_season` estimates the final episode from the next timetable episode plus the announced count at one a week, and answers `"unknown"` with a reason when either is missing. The tools return text from the `*_text` formatters at the bottom of the module; the data functions above them still return slim dicts. List headers state shared context once (season, rating cutoff, "episode counts and premiere dates are given only when announced"), and unknown values are left out rather than spelled "not announced" on every line. `user_list_text` groups shows under "Airing today/tomorrow/later this week/next week" headings, because small models filtered a flat list for "this week" unreliably. `continues_text` leads with "will NOT be airing next season", because "continues next season: no." was read as a yes. Airing lines put the name first, because "14:31 FX Fighter…" was read as a channel called FX. The season list is capped at `MAX_SEASON_LIST`. Responses are cached for an hour (the limit is 120 requests per minute). Some anime have no `names` key. `user_list` reads `config.animeschedule_user`'s public list with the app token (the `/animelists/oauth` routes need OAuth2) and is read-only on purpose. It's cached for only 60s, and English names come from the ongoing-anime cache so they match the airing tool. Each entry also gets its next subtitled episode from this and next week's timetables, so questions like "which of my shows air this week" need one tool call. Small models don't reliably chain the day-by-day airing tool themselves.

**CS tools (`cs_api.py`).** Matches, teams, players and tournaments come from PandaScore's `/csgo` routes. The free plan has no stats routes (they return 403), so player rating/K-D isn't available. It has no age in player search either; that's read from the team's roster. HLTV itself is behind Cloudflare and can't be reached with httpx. The ranking is Valve's Regional Standings: the newest `live/<year>/standings_<region>_<date>.md` from the ValveSoftware GitHub repo, parsed from its markdown table. PandaScore and Valve name some teams differently ("Team Falcons" vs "Falcons"), so `_valve_rank` drops filler words and falls back to 3+ shared roster players. PandaScore can't filter matches by tier, so "all" lists are filtered locally to `config.cs_min_tier`, but they also keep any match with a team from Valve's top `MAJOR_TEAM_RANK`, since top teams play small events too. A started match is `running`, not `upcoming`, in PandaScore, so per-team upcoming lists and `get_cs_team` also query `/matches/running`. Past "all" results are also re-sorted and capped at 30 days, because the API's sort lets in stale forfeits. Teams are searched by name and acronym, with exact matches and teams that have a roster first ("Spirit", not "Spirit Academy"). Match responses are cached for 60s, everything else for an hour. Tools return text from the formatters at the bottom of `cs_api.py`. `match_line(match, team)` writes a team's own matches from its side ("won 3-0 vs MOUZ") and other results as "X beat Y 2-0", so the model can't mix up whose score is whose. Match lists are grouped under day headings with times.

**Calendar tools (`calendar_api.py`).** Apple Calendar through EventKit (pyobjc), so every calendar synced to the Mac is visible. EventKit is blocking: tools call it with `asyncio.to_thread`. The shared `EKEventStore` is made on first use, which shows macOS's permission prompt. The permission belongs to the parent app (Terminal, VS Code). A process that can't hold it (e.g. Claude Code's own shell) gets an instant refusal with the status still undetermined, so calendar access can't be tested from there; fake `_events_between`, `_target_calendar` and `save_event` instead. `_events_between` calls `store.reset()` first: the store only learns about changes made in Calendar.app through notifications on a macOS run loop, which the app does not run, so a cached store misses new events. `parse_day` takes "today", weekdays ("next friday" is after today) and ISO dates, so the model doesn't do date arithmetic. `get_calendar_period` covers this/next week, this/next month, a month name or YYYY-MM, and multi-day lists say "days not listed have no events". `add_calendar_event` refuses past times (usually a wrong year from the model), skips an event with the same title and start that's already there (so a repeated "add NAVI's match" is harmless), and asks the user with `tools.confirm` before `save_event`. New events go to `config.calendar_name`, or Calendar's default calendar. Cross-tool requests ("put the next Frieren episode in my calendar") route to two groups because the same example question is in both `calendar` and `anime` (or `cs`).

**Confirmation (`tools.confirm`).** A tool that changes something outside the app awaits `confirm(question)`. `Chat` sets `tools.confirm_handler` on mount. It pushes a `ConfirmScreen` (y / n / escape) and waits on a thread-safe future, because tools run on the app's loop when streaming but on `fetch_response`'s own loop in a thread otherwise. Interrupting while asking closes the popup. Without a UI, `confirm_handler` is `None` and changes go through.

**Loaded file (`rag.py`).** `Chat.load_file` runs `rag.load` in a thread, shows progress in the spinner and puts the result in `Conversation.document` (`/unload` and `/clear` drop it). A file up to `WHOLE_FILE_SHARE` of `context_length` is sent whole, at the end of the system message, where it's the same every turn so Ollama reuses its cache. A longer one is chunked (paragraphs packed to `CHUNK_CHARS` with `OVERLAP_CHARS` carried over, each labelled "lines 120-148" or "page 3"), embedded with `config.rag_embed_model`, and cached in `~/.cache/deckartes/embeddings` by path, mtime, size, model and chunk settings. Each turn `Conversation.file_excerpts` picks the `TOP_K` chunks most like the question (or, at `PREVIOUS_WEIGHT`, the previous one, for follow-ups) and `messages_for` sends them as a system message just before the question, never stored in the history. `Usage.file_context` shows on the usage line. EmbeddingGemma's task prefixes (`DOCUMENT_PREFIX`, `QUERY_PREFIX`) gave clearer matches than plain text. The excerpt prompt repeats its rule after the excerpts, because granite answered from its own knowledge when the rule came only before them. Top scores for questions the file can't answer overlap with real matches (0.56-0.67 vs 0.63-0.79 on a test file), so there's no relevance cutoff: every question gets excerpts. A ctrl+c during embedding sets a `threading.Event` the loader checks between batches.

**Conversation (`conversation.py`).** `Conversation.history` holds only finished user/assistant text; tool calls and results aren't kept between turns. `stream_reply` yields display text (an error comes last, as its own paragraph) and saves the turn only after a clean finish, so a failed, cancelled or closed turn never reaches the history. `reply` is the blocking variant: it runs `fetch_response` in a thread and moves `on_tool` back onto the event loop itself. Model-calling logic goes here, not in widgets.

**Token usage.** `stream_response` / `fetch_response` add each chat call's `prompt_eval_count` / `eval_count` to an optional `Usage`, summed over tool rounds, since each round re-sends the conversation. `Conversation` keeps `last_usage` and `total_usage`, counting failed turns too because they still used tokens, and `/clear` resets both. After each reply `Chat.add_usage` mounts a `.usage` line, always. `t` toggles `config.show_token_usage`, which sets the `show-usage` class on `Chat` (CSS shows or hides every line at once) and adds the total to the Output border title (`Chat.update_usage`).

**Chat flow (`chat.py`).** On submit: `/`-prefixed input goes to `Chat.COMMANDS` (name → method name + description; the help screen reads the descriptions); otherwise `set_busy(True)` swaps the `Input` for the `Spinner` and starts the `fetch_stream` worker. The worker's `finally` always calls `set_busy(False)`. Interrupting (`ctrl+c`, a priority app binding enabled through `check_action` only while `Chat.busy` and no text is selected, so otherwise `ctrl+c` falls through to Textual's copy-selection; `copy_to_clipboard` also pipes to `pbcopy` because some terminals ignore OSC 52) cancels the worker; the worker then removes the unfinished reply bubble.

**File explorer (`file_explorer.py`, key `e`).** A `DirectoryTree` rooted at the home folder whose `filter_paths` keeps only what Finder shows (`disk_scan.is_user_facing`: no dot-files, no `UF_HIDDEN` entries like `~/Library`). The highlighted entry's size is scanned in a thread worker after `SCAN_DELAY`, capped at `SCAN_BUDGET` entries (the details line then says "at least"). Selecting a file dismisses the screen with its `Path`, and `DecartesApp.file_chosen` passes it to `Chat.load_file`.

**UI details.** The help screen is built from `DecartesApp.BINDINGS` (it uses a binding's `tooltip` when set) plus `Chat.COMMANDS`, so new ones appear without editing the screen. Rich renderables can't use Textual CSS variables like `$accent`; resolve them with `app.get_css_variables()`. Styles are in `chat.tcss`, loaded via `CSS_PATH` relative to `app.py`.
