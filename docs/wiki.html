Overview

A terminal chat (Textual) for local MLX models, served by Rapid-MLX, that can call tools.

33tools
6tool groups
1prompt preset
~4,100lines of Python

What the model can reach

  1. Home server: CPU, RAM, disk, temperatures, containers (Glances API).
  2. This computer: list folders, find files, folder sizes.
  3. Web: search and read pages (Ollama web API).
  4. Anime: seasons, ratings, airing schedule, your list (AnimeSchedule.net).
  5. Counter-Strike: teams, players, matches, tournaments (PandaScore) and Valve's ranking.
  6. Calendar: read and search Apple Calendar, add events after you confirm.
  7. Your files: save files or whole folders once and ask about them in any session.
Built for small local models: tool text is short and carefully worded so it can't be misread, and only the tools a question needs are sent.

No package, no build step, no linter, no requirements file. Dependencies live in venv/.

Setup & running

Install

  1. An Apple Silicon Mac, Python 3.11+ and a virtual environment: python3 -m venv venv.
  2. venv/bin/pip install textual textual-dev httpx pyobjc-framework-EventKit pypdf cryptography numpy (cryptography is for AES-encrypted PDFs).
  3. Install Rapid-MLX: uv tool install 'rapid-mlx[embeddings]'. The app starts its servers and stops them on exit, and the models download the first time they're needed.
  4. Put API keys in the environment or a .env next to config.py.
  5. Optional: Glances in web-server mode on the home server; macOS calendar access for your terminal app.
KeyNeeded for
OLLAMA_API_KEYweb search and page reading

Run

venv/bin/python src/main.py                   # the app
PYTHONPATH=src venv/bin/textual run --dev src/main.py  # with devtools (+ `textual console` elsewhere)
PYTHONPATH=src venv/bin/python -m unittest discover tests  # tests; live ones skip unless LIVE=1
LIVE=1 PYTHONPATH=src:tests venv/bin/python -m unittest discover tests -p 'test_live_*.py'  # live tests only
./deckartes-telegram.command                  # the Telegram bot, in Terminal (calendar access needs it)
(cd src && ../venv/bin/python -m jobs.anime_digest)  # send today's anime digest now (launchd runs it at 09:00)
If the routing embeddings fail, every allowed tool is sent with the question.

Architecture

Feature packages in src/ (core, model, agent, tools, ui, telegram, validation, jobs), in layers. Each layer talks only to the one below it.

Principles

  1. Shared mutable config. Modules read config at call time; widgets change settings by assigning to it.
  2. No UI in Conversation. Model-calling logic lives there; widgets only render events.
  3. Events, not exceptions. A turn yields events; any failure is a final Failed.
  4. One owner per concern. Time: clock.py. Names: names.py. Web HTTP: http_client.py. Model servers: mlx_client.py talks to them, mlx_server.py runs them.
  5. Prompts are data. prompts.json is re-read on every use.

Model server

Local models run in Rapid-MLX, as child processes of the app. mlx_server.py starts and stops them; mlx_client.py is the only module that talks to them.

A Rapid-MLX server holds one embedding model and rejects any other name, which is why there are two.

When servers start and stop

MomentWhat happens
App opensChat server starts; the spinner says "Starting model server...". The first start downloads the model.
Every chat or embedding callensure_chat / ensure_files run first, so a crashed server returns on the next turn
First library load or searchFile search server starts
Key m, new modelChat server restarts, since the model is a launch argument; refused while a reply is running
/killStops the servers this app started; the next question starts them again
App exitsatexit stops them

Rules

  1. A server already answering on a port is reused and never stopped.
  2. Readiness polls /health/ready, which is 503 until the model has loaded. /v1/models answers as soon as the port binds, so it can't be used.
  3. Server output goes to ~/.cache/deckartes/rapid-mlx-*.log, never the terminal the app draws on.
  4. The model picker lists the current model and the complete chat models in the Hugging Face cache.

Model flags

  1. LFM3's 4-bit build isn't in Rapid-MLX's catalog, so PARSER_FLAGS names its parsers: nemotron handles the <tool_call><function= format. A new model family that doesn't auto-detect needs an entry.
  2. Thinking is set per request (enable_thinking: on for chat turns, off for complete()). The --reasoning-parser flag makes the server stream it as reasoning_content, apart from the reply. The --no-thinking flag is a different thing: it leaves thinking tokens in the reply.
  3. EmbeddingGemma 2 must be a catalog build (-4bit or -bf16). The -8bit build fails with "Model type embedding_gemma2 not supported".
Prompt cache. The server reuses the longest identical start of the prompt: about 0.15 s to first token against 3 s cold for 1,300 tokens on an M1. So the date stays at the top and the time goes just before each question. A different set of routed tool groups is a cold start, because tools are part of the first system block.

The turn

One question and everything done to answer it. Conversation.stream_reply runs it as the fetch_stream worker.

Stages

  1. Compact the history if the last context was too big.
  2. Build the messages; pick tools.
  3. Stream a chat call; run any tool calls; repeat up to MAX_TOOL_ROUNDS = 10.
  4. A round without tool calls ends the turn and saves it.

Events a turn yields, in order

CompactingCompactedoptional→ Thinking …Text …→ToolStarted(name)ToolsDoneper round → Thinking …Text …→ end, orFailed(message)
EventChat reaction
ThinkingGreyed thinking part of the Reply, shown in Detailed mode only; Telegram and validation ignore it
TextAn answer part of the Reply (Markdown stream); the round's first text sets the spinner to "Answering..."
ToolStarted / ToolsDoneSpinner: "Using tool: name" / back to "Thinking..."; the next round starts new parts. ToolStarted also carries the call's arguments (left out of ==), shown in Detailed mode as called tool: name(key=value)
Compacting / CompactedSpinner: "Compacting conversation..." / back to default
FailedAn **Error:** paragraph

Rules

  1. History keeps only finished turns (time line, question, reply text); tool calls, results and thinking are dropped. Thinking is never sent back to the model.
  2. A round that thinks but ends with no text and no tool call fails the turn: "the model stopped before answering".
  3. A turn is saved only after a clean finish; failed, cancelled or closed turns leave no trace.
  4. Tokens count for every turn, failed ones included.
  5. Text before a tool round is followed by "\n\n", so rounds are separate paragraphs.
  6. The stream is wrapped in aclosing: closing a turn closes the connection, which stops the generation at once.
  7. A tool failure is not a turn failure: run_tool returns it as text to the model. So do tool arguments that aren't valid JSON.
  8. max_tokens and enable_thinking are always sent; temperature, top_k and repetition_penalty unless None.

What one request contains

Context compaction

Models get worse as the window fills. Before that, the history becomes a summary.

Steps

  1. A finished turn stores context_tokens = its last call's prompt + reply tokens (the real window size, tools included).
  2. The next turn checks context_tokens ≥ compact_at × context_length and that a history exists.
  3. It yields Compacting and asks the model, with no tools, to summarise the whole history (SUMMARY_PROMPT).
  4. The history becomes one system message: "Summary of the conversation so far: …".
  5. It yields Compacted and answers the question as usual.

Edge cases

CaseBehaviour
Empty summary or model errorFailed("could not compact the conversation: …"); history untouched
Summary rolesystem, so the router never takes it for the previous question
/clear or after compactioncontext_tokens back to 0
Summarising call tokensCounted in that turn's usage
compact_at = NoneNever compacts

Saved conversations

Every finished turn of the app and the Telegram bot goes to history.db, so a conversation can be reopened and continued later.

  1. Conversation(source="app" | "telegram") saves each finished turn through history.add: the time line, the question and the reply, each with its local date, plus the model name on the reply. /validate passes no source and saves nothing.
  2. The conversation's row (source, preset name, system prompt) is written with its first finished turn, so a chat that never got an answer leaves nothing behind.
  3. /clear ends the conversation: the next turn starts a new one. Closing the app or restarting the bot leaves it saved; both start with an empty chat.
  4. Compaction saves the summary as a system message and keeps the messages it replaced.
  5. Conversation.open(id) continues a saved conversation. The model gets the last summary (if any) and the turns after it; the screen shows every question and answer.

Edge cases

CaseBehaviour
Save fails (locked database, full disk)The turn still counts; NotSaved(message) follows its text. The app shows a warning, the bot logs it.
Conversation deleted while still open (e.g. the bot's)Its next finished turn starts a new conversation
Failed or interrupted turnNot saved, as with the in-memory history
Telegram conversation opened in the appContinued in the app; its source stays telegram

Prompt presets

prompts.json, selected by config.system_prompt, re-read on every use.

PresetPurposeTools
AssistantGeneral helper, used by the app and the Telegram botall
  1. system_message() always starts with the current local date, and current_time_line() puts the time just before each question, which keeps the prompt cache valid. Presets must not repeat either.
  2. Presets that have tools also get TOOL_VALUES_RULE: take values from the conversation instead of asking the user for them.
  3. The system message goes first on every turn and is never stored in the history.
  4. A new tool must be added to presets that list tools by name (not to "all").
  5. An unknown tool name raises in allowed_tool_names, showing as an error and failing tests/test_tools.py.

Library

Save a file or folder once with e; the model searches it in every later session.

Constants

NameValue
CHUNK_CHARS / OVERLAP_CHARS1500 / 200
TOP_K5 chunks per search
EMBED_BATCH16
MAX_CHUNKS / MAX_FILE_BYTES20,000 / 50 MB per file
Databaseconfig.library_path, SQLite: files and chunks with float32 vectors
  1. A file is identified by its full path. Loading it again replaces only that file, in one transaction after all its chunks are embedded, so a failed or stopped load keeps the old data.
  2. A file whose path, mtime, size, model and chunk settings are unchanged isn't embedded again.
  3. Folders are walked recursively for text, code and PDF files, without hidden files, SKIP_DIRS or symlinks. An unreadable file is reported and skipped; an embedding failure stops the load.
  4. Chunks are labelled "lines 120-148" or "page 3".
  5. Embedding runs on its own server, started the first time the library is used in a session.
  6. EmbeddingGemma's DOCUMENT_PREFIX (with the file name as title) / QUERY_PREFIX gave clearer matches.
  7. Search is brute force with numpy over an in-memory matrix, rebuilt when the database changes: 0.02 s over 100,000 chunks. Only vectors from the current rag_embed_model are searched.
  8. No relevance cutoff: unanswerable questions score like real ones, so the tool text tells the model to say when the passages don't answer.
  9. The rule is repeated after the passages, because granite ignored it when it came only before.
  10. search_library is in no tool group: the router can't know what the files contain.
  11. ctrl+c during a load sets a threading.Event checked between files and batches. Finished files stay saved.
  12. /library lists saved files and /forget removes them after asking. /clear doesn't touch the library.

How tools run

  1. tool_schema.py builds the schema from the function name, type hints and docstring. A parameter is required unless its type allows None, even with a default, so keep them few.
  2. run_tool passes str through, JSON-encodes anything else, and turns exceptions into text for the model.
  3. Docstrings say "home server (thinkpad)" vs "this computer" so the model can tell them apart.
  4. Side-effect tools call tools.confirm: a ConfirmScreen (y / n / escape). With no UI the change goes through.

Backends

A backend fetches from one source and returns tool text: a private fetch step plus a private wording step.

Glances glances_api.py

  • A few lines per call; raw JSON is mostly counters (containers ≈ 8,000 tokens).
  • overview() gathers every endpoint at once.
  • File systems de-duplicated by device.
  • Temperatures include the warning level.

Disk disk_scan.py

  • Scans capped at 200,000 entries; results then say "at least".
  • Hides what Finder hides: dot-files, UF_HIDDEN.

Web web_search.py

  • Ollama web API, needs OLLAMA_API_KEY.
  • Up to 5 results, snippets cut at 1500 chars.
  • Pages cut at 8000 chars, max 20 links.

Anime animeschedule_api.py

  • Rating 1–100 becomes 0–10; low ones dropped, unrated kept and sorted last.
  • Timetables matched to ongoing anime by route.
  • Relative seasons ("next") so the model needn't compute.
  • Final episode estimated; "unknown" with a reason if not possible.
  • User list is read-only, cached 60 s; the rest 1 hour.

Counter-Strike cs_api.py

  • PandaScore /csgo; the free plan has no stats routes.
  • Ranking parsed from Valve's GitHub standings table.
  • Team names reconciled across the two sources.
  • "All" lists filtered to cs_min_tier plus top-30 Valve teams.
  • Matches worded from a team's own side; match cache 60 s.

Calendar calendar_api.py

  • EventKit via pyobjc, run in a thread.
  • Store reset before each read to see outside changes.
  • Parses "today", "next friday", ISO dates, months.
  • Add: end is optional (one hour by default); refuses past or backwards events, skips duplicates, asks you first.

Adding a tool

Steps

  1. Add a public function to the backend: tool arguments in, tool text out.
  2. In tools.py, an async function with type hints and an Args: docstring, decorated @tool("<group>"); the body is one backend call.
  3. Choose a group, or add one to TOOL_GROUPS with example questions.
  4. Add it to presets that list tools by name.
  5. Write an exact-text test in tests/test_*_tools.py.

Design rules

  1. One tool per common question; small models don't chain calls reliably.
  2. Say so when nothing is found; an empty list invites a made-up answer.
  3. Make a value the model often lacks optional; LFM3 asks the user for required ones.
  4. Short plain text with units (GB, %, °C) instead of raw JSON; include limits and totals.
  5. Cap returned size to fit the context window.
  6. @tool(None) = in no group, sent with every question.
  7. Changes outside the app must go through tools.confirm.

UI & keys

DecartesApp owns screens and bindings; Chat owns bubbles, spinner, busy state and interrupt.

Keys

  • q quit
  • m model
  • c config
  • e file explorer
  • r history panel (enter open, d delete)
  • h help
  • shift+t Default / Detailed mode
  • ctrl+c interrupt (copy if text selected)

Commands

  • /clear end the conversation (it stays in the history)
  • /kill stop the model servers
  • /library list saved files
  • /forget remove saved files
  • Typing / opens a filtered suggestion list (Up/Down, Tab or Enter completes, Esc closes)

Submit flow

  1. On mount the input waits behind the spinner until the chat server is ready.
  2. Input starting with / goes to Chat.COMMANDS.
  3. Anything else: set_busy(True) swaps the input for the spinner and starts fetch_stream.
  4. Events render; tool labels stay at least 1 s.
  5. The worker's finally always calls set_busy(False).
  6. Interrupt cancels the worker, which removes the unfinished bubble; the history is untouched.

File explorer

  1. A DirectoryTree at the home folder shows only what Finder shows.
  2. The highlighted entry's size is scanned in a thread after 0.3 s, capped at 50,000 entries.
  3. Selecting a file returns its Path to DecartesApp.file_chosen, then Chat.load_file.
