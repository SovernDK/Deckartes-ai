# Tool routing (`tool_router.py`)

Tool definitions are most of the prompt (~2,700 tokens for all tools, against 90 for "hi" without them). So `select_tools(messages)` owns the whole choice: it takes the tools the preset allows (`prompts.allowed_tool_names`) and narrows them to the groups `_route()` picks, returning a `Selection(tools, groups)`. It embeds the question with `config.embed_model` and compares it with each group's `examples` and with `NO_TOOL_EXAMPLES`. Groups at or above `CONFIDENT` and within `MARGIN` of the best are sent. Otherwise small talk gets no tools, a vague question borrows the previous question's scores (`PREVIOUS_WEIGHT`), and so does a short follow-up (`FOLLOW_UP_WORDS`, `FOLLOW_UP_STARTS`: "and tomorrow?") even when it's confident on its own, since "tomorrow" alone matches calendar, and an unsure question gets the top `UNSURE_GROUPS` groups, because unknown names (a player, a show) score low. Tool routing is tested in `tests/test_tool_router.py`: rule tests use fake vectors in place of `_embed`, and `LIVE_CASES` runs real questions through the embedding model. Rerun it if you change the embedding model, the examples or the thresholds, and add examples rather than lowering thresholds. Routing is skipped when the preset's tools sit in a single group, tools in no group are always sent, and any router error falls back to every allowed tool. Embeddings use the cached async client, which is bound to the app's loop; every turn runs there. Example embeddings are computed once per host+model. `stream_response` copies `Selection.groups` into `TurnInfo.tool_groups`, which shows on the usage line ("tools: cs").
